# Codex App app-server integration POC evidence

Date: 2026-07-15 (Asia/Shanghai)

## Result

**No-go for direct HUD integration with the currently running Codex Desktop app-server.**

The protocol is structured and useful, but Codex Desktop 26.707.71524 owns a private stdio app-server process. On Windows there is no supported daemon/control-socket attachment path, and a second app-server process can read persisted threads but cannot observe the Desktop process's loaded threads or live notifications without calling the stateful `thread/resume` rejoin operation.

## Live baseline

- Desktop process: PID 16608, CDP listener `127.0.0.1:58655`.
- Desktop-owned app-server: PID 4452, parent PID 16608.
- Command: bundled `codex.exe ... app-server --analytics-default-enabled`; no `--listen` override, so transport is the default `stdio://`.
- PID 4452 had no TCP listener. The only listener owned by the Desktop process family was the Electron CDP port.
- CDP exposed the main renderer and `/avatar-overlay` targets before and after the POC.
- Main renderer selected canonical session at the POC boundary: `019f6359-2359-7192-8717-5097179c1e7c`.

## CLI and transport evidence

Bundled CLI version: `codex-cli 0.144.2`.

`app-server --help` advertises:

- `stdio://` (default)
- `unix://` / `unix://PATH`
- `ws://IP:PORT`
- `off`
- `daemon` and `proxy` management commands

This does not make the existing Desktop stdio process attachable:

- Desktop did not start a Unix socket or WebSocket listener.
- `app-server daemon version` on this Windows host failed with `daemon lifecycle is only supported on Unix platforms`.
- `app-server proxy` connects to a running Unix-domain control socket and therefore cannot attach the Windows Desktop stdio process.
- Starting a separate WebSocket app-server would create a separate server/process; Desktop is not connected to it.

## Schema evidence

The experimental JSON schema generated by the bundled 0.144.2 binary contains read requests and a full notification model:

- Safe persisted reads: `thread/list`, `thread/read`, `thread/turns/list`, `thread/items/list`, `thread/loaded/list`.
- Live lifecycle notifications: `thread/status/changed`, `turn/started`, `item/started`, item deltas, `item/completed`, `turn/plan/updated`, `turn/completed`, and token-usage updates.
- Waiting/request lifecycle appears as server requests for command execution, file changes, permissions, user input, MCP elicitation, and dynamic tool calls.

Important subscription boundary:

- There is `thread/unsubscribe`, but no `thread/subscribe` or generic read-only attach request.
- `ThreadResumeParams` documents that, when `threadId` identifies a running thread, app-server **rejoins that thread**.
- `thread/resume` accepts approval, reviewer, configuration, cwd, model, permissions, sandbox, service tier, and runtime workspace override fields. It is therefore a stateful session operation, not an observation-only subscription.

Core notification identity fields are stable within this generated schema:

- `thread/status/changed`: `threadId`, `status`.
- `turn/started` / `turn/completed`: `threadId`, `turn`.
- `item/started`: `threadId`, `turnId`, `item`, `startedAtMs`.
- `item/completed`: `threadId`, `turnId`, `item`, `completedAtMs`.
- delta events: `threadId`, `turnId`, `itemId`, `delta`.
- plan updates: `threadId`, `turnId`, `plan`, optional `explanation`.

The app-server thread ID is the canonical UUID that can align with the HUD `sessionId`. A provisional `client-new-thread:*` value remains outside this canonical contract.

## Isolated stdio experiment

Two short-lived bundled app-server processes were started. Both performed only:

1. `initialize`
2. `initialized`
3. `thread/loaded/list`
4. `thread/list` or `thread/read`
5. six seconds of passive stdout observation

No `thread/resume`, `thread/start`, turn operation, approval response, metadata update, archive, or unsubscribe was sent.

### Completed selected thread

- Isolated PID 25956 initialized successfully.
- `thread/loaded/list` returned `[]` before and after `thread/read`.
- `thread/read(019f6359-...)` returned persisted history with `status.type = notLoaded`.
- Six seconds of passive observation produced no turn/item notifications.
- Process exited normally on stdin EOF with no stderr output.

### Current Codex session

- Isolated PID 25108 initialized successfully.
- `thread/list` returned persisted threads, all represented as `notLoaded` in the isolated process.
- `thread/read(019f6501-bc4a-75f3-8151-6a55d87cf16e)` succeeded and returned persisted turn metadata, again with `status.type = notLoaded`.
- The target was absent from the default first `thread/list` page but directly readable by canonical ID.
- `thread/loaded/list` remained `[]` after the read.
- Six seconds of passive observation produced no turn/item notifications.
- Process exited normally on stdin EOF with no stderr output.

This proves persisted visibility and live-stream visibility are separate. Read/list operations do not attach the observer to the Desktop process's in-memory stream.

## Non-interference audit

- Desktop app-server PID 4452 and parent PID 16608 remained unchanged.
- No additional app-server process remained after either isolated experiment.
- Desktop app-server still had no TCP listener; CDP remained on 58655.
- Main and avatar CDP targets remained available.
- The POC sent no stateful thread method and caused no Desktop reconnect or new app-server start.
- The Desktop renderer had user-side active-session changes during the observation window, but the POC boundary selected the same canonical session before and after. These renderer events did not originate from the isolated app-server processes.

## Platform and stability matrix

| Surface | Windows live result | macOS status | Stability |
|---|---|---|---|
| Generated JSON schema | Confirmed | Expected from same CLI, not live-tested | Versioned per bundled CLI, experimental fields may drift |
| Desktop stdio transport | Confirmed private child process | Not live-tested | Not attachable after process start |
| Managed daemon/control socket | Explicitly unsupported | CLI says Unix-only; not live-tested | Potentially available but still requires client subscription semantics |
| WebSocket listener | Supported when starting a server explicitly | Expected, not live-tested | Does not expose an already-running stdio Desktop server |
| Read/list from isolated server | Confirmed persisted-only | Not live-tested | Safe but not real-time |
| Live stream join | Only `thread/resume` found | Same schema expected | Stateful; may change role/config and requires explicit risk acceptance |
| Electron renderer store | Confirmed package-private | Not live-tested | Private, release-sensitive, not a HUD contract |

Even if a Unix daemon permits multiple proxy clients on macOS, the generated protocol still exposes rejoin through `thread/resume`, not a read-only subscription. A macOS experiment would be required before claiming otherwise, but it would not solve the Windows cross-platform requirement.

## Decision

Do not integrate the HUD with Codex Desktop's current app-server instance.

Continue using the local canonical-session mapping, rollout/session-file events, and structured `WorkStatusItem` projection. A future app-server integration would require Codex Desktop itself to expose one of:

- a documented read-only observer connection to its existing server;
- a versioned subscribe/attach method that cannot alter stream role or thread configuration; or
- a supported cross-platform shared daemon architecture used by Desktop and HUD together.

Without one of those product-level contracts, calling `thread/resume` merely to obtain notifications is not an acceptable HUD dependency.
